Ruth — Biblical Scholar Blueprint
Sep 17, 2026 · @Michelle
Overview
Ruth is a local, fully offline conversational research assistant grounded in a curated library of roughly one hundred primary and secondary texts: scripture across several canons, the works of Josephus, Dead Sea Scroll material, apocryphal writings, and the Jewish histories. She runs entirely on local hardware with no API keys, no cloud dependency, and no per-query cost.
The governing design principle is that the system answers from its own corpus rather than from the language model's training data. A general-purpose model asked about the Second Temple period will produce a fluent paragraph assembled from whatever it absorbed during training. Ruth receives actual passages retrieved from the indexed library before generating anything, framed as recalled knowledge, and is instructed to remain within them.
The second design goal was conversational register. Ruth is written to speak as a scholar in dialogue rather than as a reference work: two to five sentences, no bullet points, no headings, no unsolicited offers to expand into adjacent topics. This required deliberate enforcement, since instruction-tuned models default strongly toward expository mode and will not moderate themselves without explicit constraint.
Ruth is the first character built on this architecture. The pipeline is intentionally general — additional figures such as Moses, David, or Solomon can be produced by substituting the source library and the identity block, with no structural changes.
Architecture
Seven stages execute per query. Only two involve the language model.
flowchart TD
  A[Question received] --> B[Embed the query]
  B --> C[Chroma: 30 nearest chunks]
  C --> D[Filter: distance + per-source cap]
  D --> E[Build system prompt<br/>passages framed as recall]
  E --> F[Ollama: llama3.2]
  F --> G[Post-process: strip markdown<br/>and trailing offers]
  G --> H[Kokoro TTS: bf_emma]
The separation is deliberate and makes failures diagnosable. Stages B through D are vector search and remain fast even without GPU acceleration. Stage F accounts for essentially all response latency. Stages G and H are negligible.
The implementation is two Python files. ingest.py runs once per batch of new source material and builds the index. ruth.py is the conversation loop. The two share filesystem locations through ruth_paths.json, written by the ingest stage and read by the conversation loop, which eliminates an entire class of configuration drift between them.
Corpus and Ingestion
The collection holds 42,399 chunks indexed in ChromaDB.
ingest.py walks the source directory, extracts text from every PDF and plain-text file via pypdf, and divides each document into 1,200-character chunks with 200 characters of overlap, so that a passage split across a boundary still appears intact in at least one chunk. Every chunk is persisted with its source filename, title, and page range.
ChromaDB replaced an earlier FAISS implementation. FAISS stores vectors alone, which meant the mapping from vector position back to source text lived in a separately maintained pickle file — fragile, with no metadata, and prone to desynchronization whenever documents were re-chunked. Chroma co-locates text, embedding, and metadata in a single persistent store. That metadata is what makes both the source-diversity filter and the retrieval diagnostics possible.
Embeddings are generated by all-MiniLM-L6-v2 through sentence-transformers. The same embedding model must be used at index time and at query time; a mismatch returns plausible but meaningless results with no error raised.
Ingestion is idempotent. Documents already present are skipped by source name, so expanding the library is a matter of adding files and re-running the script.
Four source files yielded no extractable text and were skipped — scanned page images carrying no text layer. Making them usable would require an OCR pass through ocrmypdf and Tesseract. At four documents out of roughly one hundred, this was deprioritized.
Retrieval and Source Diversity
Retrieval fetches 30 candidates, then admits at most 2 from any single source until 5 passages are selected. The wide candidate pool combined with a per-source cap is the core retrieval design.
Without the cap, corpus volume dominates results. A query about Josephus and Jesus returned three chunks from one Ethiopian Bible edition and one from Tyndale: scripture text scores well against "Jesus," and a source contributing thousands of chunks has thousands of opportunities to place. Antiquities of the Jews sat indexed and unconsulted while the model answered from gospel narrative. With the cap applied, the same query drew from the Josephus material and the Jewish histories, with sixteen competing chunks displaced.
Distance is cosine, configured at collection creation via hnsw:space: cosine and matched across both scripts. Lower values indicate closer semantic match:

A diagnostic block printed before each response marks every candidate as used, capped, or rejected, with its distance score and source attribution. This separates retrieval failures from generation failures — two distinct problems requiring different remedies — and turns an opaque pipeline into an inspectable one.
One known interaction: duplicate files defeat the cap, since each copy receives its own allowance. Two filenames returning the same page at an identical distance score is the signature of a duplicated source.
Prompt Design
The placement of retrieved text within the message structure proved to be the single most consequential decision in the build.
Passages placed in the user message are interpreted by the model as a document submitted for review. It summarizes them, comments on them, quotes them back, and produces constructions such as "the text provided suggests." This was the original failure mode — responses that read as encyclopedia entries — and it was never a retrieval defect. It was message placement.
Passages placed in the system message, framed as the character's own recall, produce speech from the material rather than commentary on it. The framing is explicit: these are memories from years of study, to be drawn on silently and never referred to as documents, sources, or context.
The assembled prompt has four ordered components:
1. Identity — character, register constraints, honesty rules
2. Recall — retrieved passages, framed as memory
3. Exemplars — two short exchanges demonstrating the target voice
4. History — the last six exchanges, followed by the current question
The exemplars carry disproportionate weight. A 3B-parameter model reproduces demonstrated voice far more reliably than it follows descriptive adjectives; two worked exchanges outperform a paragraph of instruction about tone.
Three register constraints are load-bearing. Prohibiting closing offers prevents every turn ending in "would you like to know more about…". Prohibiting markdown prevents bulleted answers. Specifying a two-to-five sentence target prevents lecturing. MAX_TOKENS serves as a hard backstop when prompt-level constraints fail.
A post-processing pass strips residual markdown and removes a trailing offer if one survives generation.
Runtime Stack
Generation. Ollama serves llama3.2 over HTTP at localhost:11434/api/chat. The service must be running; if it stalls or unloads, the client blocks with no error surfaced until timeout. ollama ps reports whether a model is resident and whether it is executing on GPU or CPU.
Speech synthesis. Kokoro provides the voice, configured to bf_emma. Any Kokoro voice can be substituted by changing a single constant; the script derives the language code from the voice prefix, so British and American voices are selected automatically. Kokoro model loading accounts for a substantial share of startup time, and a flag disables speech entirely to accelerate iteration during development.
Speech recognition. Whisper is integrated but disabled by default. When enabled, a keypress starts recording, a second keypress ends it, and the transcription is submitted as the query. It was kept off during initial development so that answer quality could be evaluated without transcription accuracy as a confounding variable.
The conversation loop also accepts typed commands: books prints every indexed title with its chunk count, quiet and loud toggle speech output, and quit exits.

Known Limitations
Latency. Response time is approximately two and a half minutes. Generation currently executes on an i7-4790 CPU; the installed GTX 1660 is unavailable pending a power supply replacement. Roughly 1,500 tokens of retrieved context must be processed before the first token is generated. The earlier FAISS implementation appeared faster only because it was supplying the model with almost no context.
Fabricated references. The most significant remaining weakness. Chapter-and-verse citations are short, highly patterned strings — precisely what a 3B-parameter model generates convincingly without grounding. Compounding this, PDF text extraction typically discards verse structure, so even when drawing on a genuine passage the model has no reference available and produces one. In testing, a citation was generated for a verse present nowhere in the corpus, and was retracted only when challenged directly.
Behavior on empty retrieval. When no chunk clears the distance threshold, the model receives the identity prompt alone and cannot distinguish "nothing was recalled" from "nothing was supplied." It extrapolates rather than declining. Making the empty-retrieval case explicit in the prompt is the identified remedy.
Contested scholarship. On disputed material such as the Testimonium Flavianum, which passages happen to surface determines which scholarly position the response reflects, and a model of this size will not signal that it is presenting one reading among several.
Corpus gaps. Four documents require OCR. One Greek and Latin edition extracted only two chunks, indicating font-encoding failure or image-only pages, leaving it effectively absent despite appearing successfully indexed.
Roadmap
Planned work, in order of expected payoff.
Response streaming. The largest available improvement at no computational cost. Setting stream: True and emitting tokens as they arrive surfaces the first words within twenty to thirty seconds rather than after a silent two-and-a-half-minute wait. Total generation time is unchanged; perceived responsiveness is transformed.
Model persistence. Adding keep_alive to the request payload prevents Ollama from unloading the model between queries, eliminating reload time following any idle period.
GPU acceleration. Completing the power supply replacement enables the GTX 1660 and moves generation off CPU, which is expected to reduce response time from minutes to seconds.
Model upgrade. llama3.1:8b is materially better at acknowledging uncertainty, which addresses the fabricated-citation problem directly. It roughly doubles CPU inference time, so it is sequenced after GPU acceleration.
Citation suppression. Prohibiting chapter-and-verse output entirely, requiring locations to be described in prose instead. Blunt, but a model of this size cannot reliably distinguish a remembered reference from an invented one.
Additional characters. Moses, David, and Solomon on the same pipeline with substituted corpora and identity blocks. Ruth serves as the validated template.
